### 📝 기능 구현 목록

#### 로그인
- [x]  사용자는 로그인할 수 있다.
- [x]  로그인에 성공하면 이후 요청에서 같은 사용자를 식별할 수 있어야 한다.
- [x]  로그인에 실패하면 적절한 응답을 반환한다.

#### 예약 생성
- [x]  로그인한 사용자는 예약을 생성할 수 있다.
- [x]  예약 생성 시 요청으로 받은 이름이 아니라 로그인한 사용자를 기준으로 예약을 만든다.
- [x]  로그인하지 않은 사용자는 예약을 생성할 수 없다.

#### 예약 조회
- [x]  로그인한 사용자는 자신의 예약을 조회할 수 있다.
- [x]  로그인하지 않은 사용자는 인증이 필요한 예약 조회 기능을 사용할 수 없다.

#### 인증 공통 처리
- [x]  로그인 여부 확인 로직을 컨트롤러마다 반복하지 않는다.
- [x]  인증이 필요한 API와 필요하지 않은 API를 구분한다.
- [x]  인증 실패 시 일관된 응답을 반환한다.

#### 구현 조건
- [x]  Spring Security를 사용하지 않는다.
- [x]  세션 또는 직접 구현한 인증 흐름을 사용할 수 있다.
- [x]  인증에 필요한 공통 처리는 Interceptor, ArgumentResolver 등 적절한 도구를 사용해 분리한다.
- [x]  컨트롤러는 가능한 한 로그인 사용자 정보를 직접 꺼내지 않는다.

#### 로그인 상태 유지 방식
- 세션을 사용 
  - 현재 규모에서는 서버 메모리를 활용하는 세션 방식이 구현이 직관적이고, 강제 로그아웃등 상태 제어를 서버에서 관리할 수 있어 보안상 유리하다고 판단했습니다.

#### 인증이 필요한 API를 구분하는 방식
- 커스텀 어노테이션(`@LoginRequired`, `@AdminOnly`)을 사용했다.
  - Interceptor 설정에서 URL 패턴으로 관리하면 API가 추가/변경될 때마다 설정 파일을 수정해야 하고 누락될 위험이 있습니다. 
  - 어노테이션을 쓰면 컨트롤러 메서드만 봐도 인증 필요 여부를 직관적으로 알 수 있어 응집도가 높아진다고 생각했습니다. 
  - 파편화된다는 단점은 있지만, 현재 규모에서는 괜찮다고 판단했습니다.

#### 인증 공통 처리 위치
- Interceptor + ArgumentResolver를 각자의 역할에 맞게 분리해서 사용
  - Interceptor: 비즈니스 로직에 진입하기 전, 세션 유효성을 검증하고 미인증 사용자의 요청을 막는 역할을 담당합니다.
  - ArgumentResolver: 검증이 끝난 후, 세션에서 사용자 ID를 꺼내 `User` 객체로 변환해 컨트롤러 파라미터에 주입합니다.
    - 컨트롤러는 `HttpSession`이나 `HttpServletRequest`에 의존하지 않고 `@LoginMember User loginUser`로 로그인 사용자를 받습니다.

#### 인증 실패 응답 방식
- 미인증: 401 Unauthorized와 `”로그인이 필요합니다.”`
- 권한 부족(관리자 전용): 403 Forbidden과 `”관리자만 접근 가능합니다.”`
